# Handoff Report: Data Privacy, Security & Core Flow Audit

**Project Name**: Style This (formerly "Det Digitale Atelier")
**Role**: Magda, Data and Privacy Specialist
**Objective**: Assess data handling, user privacy, database constraints, Row Level Security (RLS), and absolute data provenance (Data Source Audit Trail as per EU AI Act) for the "Style This" application. Specifically evaluate whether the application supports the core flow of starting from one's own body and/or one's own favorite piece of clothing from a data compliance perspective.

---

## 2. Logic Chain

1. **Body-First / Clothing-First Data Integrity & Privacy**:
   - **Step 1**: The user's body measurements, shapes, insecurities (e.g., hiding a stomach), and wardrobe contents constitute sensitive personal data. Under GDPR, storing free-text descriptions of physical attributes increases data exposure risks.
   - **Step 2**: Relying on free-text inputs for "starting from one's own body" means users might type unstructured personal descriptions or PII.
   - **Step 3**: The clothing-first flow is completely unimplemented.
   - **Conclusion**: The current architecture does not support the core flow as a structured feature. To support it securely, the application needs a structured body/clothing data model that minimizes raw text storage.

2. **Row Level Security (RLS) Enforcement**:
   - **Step 1**: Boardroom Manifestet Rule 8 states: *"Ingen database-tabel må eksistere uden stærk Row Level Security (RLS)."*
   - **Step 2**: Based on the package dependencies and local files (`package.json`, `page.tsx`), the application currently uses no database at all.
   - **Step 3**: Since no database tables exist, RLS is not currently bypassed, but it is **not enforced** either, because there is no backend architecture. 
   - **Conclusion**: RLS is a structural gap that must be addressed from day one if any features requiring state persistence (e.g. Wardrobe, Discover, Profile) are introduced.

3. **Data Source Audit Trail (EU AI Act)**:
   - **Step 1**: The EU AI Act requires user-facing algorithmic/AI decision engines to support traceability, automatic logging, and verifiable data provenance.
   - **Step 2**: The current algorithm (`getStyleAdvice`) outputs styling recommendations based on user input. The sources (`Curvii` and `W! DK`) are hardcoded in comments and static objects.
   - **Step 3**: The user's query (`val`), matching rule (`advice.rule`), and selected parameters (`colorState`) are not logged, hashed, or stored. There is no trace showing which inputs led to which output or proving the integrity of the logic.
   - **Conclusion**: There is no Data Source Audit Trail, violating EU AI Act standards and Rule 8 of the Boardroom Manifestet.

4. **Privacy by Design**:
   - **Step 1**: GDPR requires special category personal data (e.g., physical dimensions/flaws the user seeks to camouflage) to be processed under strict consent, minimisation, and security constraints.
   - **Step 2**: User queries describing physical traits (such as "mave" / "abdominal camouflage") are typed into a standard text field and processed as raw text on the client.
   - **Step 3**: If these queries are synced to a server in the future, transmitting and storing them in plain text without sanitization, encryption, or explicit consent poses a severe compliance risk.
   - **Conclusion**: The current architecture is "privacy-safe" only because it is completely local, but it lacks the encryption, sanitization, and data lifecycle management required for a secure, cloud-enabled release.

## 4. Conclusion & Compliance Assessment

The current version of the application is a stateless frontend mock. It does not violate privacy by storing data insecurely, but it represents a **critical architectural gap** for production release due to the total absence of database security, data provenance logging, and input sanitization. 

Furthermore, the core concept of **starting from one's own body and/or favorite piece of clothing** is not supported in a structured or secure way:
- **Body-first flow** is handled via sensitive, unstructured free-text search.
- **Clothing-first flow** is completely missing.

## 5. Actionable Recommendations

### Recommendation 1: Redesign the Core Flow for Structured Data Inputs
To support the body-first and clothing-first flows securely:
1. **Body-First**: Replace the free-text query with structured body profile toggles. For example, selectors for `waist_type` (`high_waist`, `mid_low_waist`) and `focus_area` (`abdominal_camouflage`, `torso_elongation`). This ensures **data minimization** (avoiding sensitive text logging).
2. **Clothing-First**: Introduce a wardrobe inventory database. Users can register their "favorite piece of clothing" (e.g., Category: Trousers, Color: Navy, Fit: Wide Fit). This data should map to the `stylingLogic.ts` definitions.

### Recommendation 2: Establish Supabase/PostgreSQL RLS Architecture
To support user profile and wardrobe saves without violating Rule 8:
1. Initialize a PostgreSQL/Supabase instance.
2. Create tables:
   - `user_profiles` (stores body structure variables like `waist_type`)
   - `wardrobe_items` (stores favorite clothing items)
3. Enable RLS on all tables:
   ```sql
   ALTER TABLE user_profiles ENABLE ROW LEVEL SECURITY;
   ALTER TABLE wardrobe_items ENABLE ROW LEVEL SECURITY;
   ```
4. Define RLS Policies restricting data access strictly to authenticated owners:
   ```sql
   CREATE POLICY "Users can only manage their own profile" 
   ON user_profiles
   FOR ALL 
   USING (auth.uid() = user_id)
   WITH CHECK (auth.uid() = user_id);
   ```

### Recommendation 3: Implement an Immutable Data Source Audit Trail
To comply with the EU AI Act's data provenance guidelines:
1. Create an append-only audit log table `styling_recommendation_logs`:
   ```sql
   CREATE TABLE styling_recommendation_logs (
       id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
       user_id UUID REFERENCES auth.users(id),
       body_profile_snapshot JSONB NOT NULL, -- Hashed or structured parameters
       clothing_item_snapshot JSONB,
       rule_applied VARCHAR(100) NOT NULL, -- e.g. "abdominal_camouflage.apply.vertical_lines"
       advice_title VARCHAR(100) NOT NULL,
       source_provenance VARCHAR(100) NOT NULL, -- e.g. "Curvii vs. W! DK Conflict Resolution"
       integrity_hash VARCHAR(64) NOT NULL, -- HMAC-SHA256 signature of log fields
       created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
   );
   ```
2. Enable RLS on `styling_recommendation_logs` allowing only **Insert** actions for authenticated users (no updates, no deletes allowed).

### Recommendation 4: Enforce Privacy-by-Design on User Inputs
Before sending styling queries to any backend or logging system:
1. **Sanitize Inputs**: Implement a utility to strip potential PII (emails, names) from queries.
2. **One-Way Hashing**: If input queries are logged for tuning, store only their one-way hashes (e.g. SHA-256) to verify match performance without exposing raw physical statements.
3. **Data Consent & Deletion**: Add a privacy consent checkbox on first use, and implement a "Purge My Styling Data" button inside the Profile tab that triggers a cascade delete across RLS-secured tables.
